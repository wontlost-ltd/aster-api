# ADR 0034：What-If 重做——异步 ReplayBatch 模型

- 状态：**PROPOSED**（2026-08-08）
- 取代：[ADR 0033](0033-whatif-replay-correlation-model.md) 的 §3（按需同步重求值）
- 继承：0033 的 §2（能力已存在）、§3.1 的关联键洞见、§4 护栏、§5.1 S0 实测

---

## 0. 一句话

What-If 要回答「把策略从 v1 换成 v2，业务指标会怎样」。
重做的形态是：**用户显式选定时间窗口 → 窗口内全量执行异步重跑 → 全部成功才出数字，
任一条失败即整批拒答**。

---

## 1. 为什么重做：上一版死在哪

Phase 4 五轮评分 52 → 43 → 58 → 48 → 47，无收敛，第十二轮判定撤下。
**决定性的一条是选择偏差**，必须写清楚，否则重做会再踩：

上一版允许「200 条发起、30 条成功」就对这 30 条出完整业务数字。
但重跑失败**与输入、词汇、策略路径相关**——若 80% 因某类输入失败，
剩下 20% 就是被筛选过的子群，不是随机样本。据此算出的正面率与金额
可能方向对而幅度全错，甚至方向本身有偏。

**这不是加 caveat 能解决的**：它是用非随机样本冒充总体影响。
前几轮一直在修「数字算错了」，而真正的问题是「这批数字凭什么代表总体」。

### 1.1 本 ADR 的第一性约束

> **任何被呈现的数字，其样本必须是某个用户能理解的总体的全量，而非该总体的成功子集。**

下面所有设计都是这条约束的推论。若某个方案违反它，无论多方便都不采纳。

## 2. 决策：异步 ReplayBatch + 用户可选时间窗口

### 2.1 两条被否的替代方案

| 方案 | 否决理由 |
|---|---|
| **同步 + fail-closed**（0033 形态的修正版） | 消偏差有效，但「一条脏数据全废」在大策略上几乎必然触发——用户永远拿不到结果。且 HTTP 超时把样本上限锁死在几百条量级，业务价值受限。 |
| **同步 + 部分成功估算** | 即上一版。**违反 §1.1**，已被五轮审查证伪。 |

### 2.2 采纳形态

```
用户选定窗口（如「近 30 天」/「全部」）
        ↓
创建 ReplayBatch（PENDING）——记录窗口口径、base/target 版本、planned 总数
        ↓
异步 worker 逐条重跑（运行与查询分离，可跨请求、可重试）
        ↓
    ┌── 全部成功 → COMPLETED → 出数字
    └── 任一失败 → FAILED    → 拒答 + 报告失败原因分布
```

**时间窗口是显式口径，不是隐形抽样。**
UI 上必须写「本结果基于近 30 天全部 N 条可重跑执行」——
用户知道自己在看什么总体，这与「从 200 条里挑出成功的 30 条」有本质区别。

### 2.3 关联键（继承 0033 §3.1，不变）

关联键**不是 `executionId`**，而是「同一条 input」。
`Execution.id` 是主键、`policyVersion` 是普通列，同一 id 不可能同时属于两个版本，
跨版本交集**结构上恒为空**。所以对照只能来自**重跑**：

```
(sourceExecutionId → 用它的 input 在 targetVersion 上重跑得到的 decision)
```

## 3. 数据模型

### 3.0 ★批次编排落在 aster-cloud，不是 aster-api（2026-08-08 修订）

**起因**：S3 接线时才查明 `executions` 表**属于 aster-cloud**（`@/lib/prisma`），
aster-api 侧根本没有这张表。而本 ADR §3 原先隐含假设 aster-api 能直接查
窗口内的执行——这个前提不成立。

考虑过的三条路：

| 方案 | 否决/采纳理由 |
|---|---|
| aster-api 反向调 cloud 内部 API 取执行列表 | ❌ 现有内部调用都是 **cloud→api 单向**，反向要新建 HMAC 通道、新的鉴权面。为一个功能引入反向依赖，代价与风险都不划算。 |
| api 侧新建执行索引表，cloud 写执行时同步 | ❌ 引入跨库一致性问题。索引漂移会让 `plannedCount` 与真实窗口不符——而窗口口径的准确性正是 §1.1 的地基。 |
| **cloud 侧驱动批次**（采纳） | ✅ **数据在哪，编排就在哪**。cloud 查执行、逐条调 api 的 `evaluate-source?simulate=true`，api 只负责「重跑一条」这件它本来就会的事。不新建通道、不引入跨库一致性。 |

**职责划分**：

```
aster-cloud                              aster-api
  · replay_batch 表（本节 schema）          · evaluate-source?simulate=true
  · 窗口解析与固化（§3.3）                     （已上线，HMAC 门控）
  · 批次状态机（§3.1 规则不变）              · PermitLease 并发背压
  · 逐条重跑编排 + 判定（§1.1 无阈值）          （已上线，#222）
  · 并发上限判定（读 PlanInfo）             · 不感知批次概念
```

**已在 aster-api 完成、需要迁移的部分**：表结构、状态机规则、判定逻辑
（尤其「任一失败即整批拒答、无阈值」）、失败分类、sealed 二选一结局。
这些是**与语言无关的设计**，直译成 TypeScript 即可；
其中的不变量与变异验证清单必须一并带过去，不能只搬代码不搬测试。

**aster-api 侧原型的处置**：撤下（表 + 状态机 + 判定逻辑）。
留着一张没有消费方的表比没有更糟——它会让后来者以为批次在 api 侧。

### 3.1 ReplayBatch 表（落在 aster-cloud）

| 字段 | 说明 |
|---|---|
| `id` | 批次主键 |
| `tenantId` / `userId` | **租户隔离必需**；所有读写一律带 `eq(userId)` |
| `policyId` | 被比较的策略 |
| `baseVersionId` / `targetVersionId` | 两个版本的行 id（不是版本号字符串） |
| `windowKind` | `LAST_MONTH` / `LAST_QUARTER` / `LAST_HALF_YEAR` / `LAST_YEAR` / `CUSTOM`（显式口径，进 UI 文案）——见 §7.1 |
| `windowLabel` | 呈现用的口径文案（如「最近一个季度」），与数字同屏显示 |
| `windowFrom` / `windowTo` | **创建时固化的绝对时刻**，左闭右开；右边界取当天 00:00（不含当天）——见 §3.3 |
| `windowTimezone` | 解析「当天」所用的租户时区（如 `America/New_York`）；未配置时为 `UTC` 并需在结果里标注 |
| `plannedCount` | 窗口内可重跑执行总数，创建时确定 |
| `completedCount` / `failedCount` | 进度 |
| `status` | `PENDING` / `RUNNING` / `COMPLETED` / `FAILED` / `EXPIRED` |
| `failureReasons` | 失败原因分布（JSON），拒答时回报给用户 |
| `toolchainId` | 创建时的工具链身份，用于判断结果是否仍可信 |
| `createdAt` / `finishedAt` | |

### 3.2 为什么这次要落表（推翻 0033 §3.2）

0033 拒绝落 `ReplayComparison` 表，理由是失效语义复杂、口径不如重跑诚实、零 schema 变更。
**那些理由在同步模型下成立，在异步模型下不成立**——必须诚实说明这个反转：

- 异步的本质就是**运行与查询分离**，中间状态**必须**可持久化，否则进程重启即丢失。
- 落的不是「预计算对照表」，而是**一次批次运行的账本**。它不试图长期有效，
  只记录「这一次、在这个窗口、用这个工具链跑出了什么」。
- 失效语义因此简单：批次是**不可变快照**，不需要失效重算；
  策略源码变了就是新批次，旧批次仍如实反映它当时跑的东西。

**注意**：只落 batch 元数据与聚合结果，**不落逐条 targetDecision**——
那才是 0033 真正想避免的东西（PII 面扩大 + 失效语义复杂）。

### 3.3 窗口边界：右边界取当天 00:00，并固化成绝对时刻

**两条规则，缺一不可。**

#### 规则一：右边界是「当天 00:00」，不是 `now()`

窗口取 `[当天00:00 - N天, 当天00:00)`——**不含当天**。
右边界指向一个已经封闭的过去，正在写入的数据天然落在窗口外。

这比取 `now()` 更稳：`now()` 会把边界切在数据正在写入的位置，
虽然固化后不再漂移，但「边界那一刻的执行算不算」本身就是个模糊地带
（写入时刻 vs `createdAt` 时刻、事务可见性）。取 00:00 让这个问题消失。

代价是**今天的执行永远看不到**。这是可接受的——What-If 回答的是
「换版本会怎样」，一天的延迟不影响判断；而边界干净带来的可复现性更值钱。

#### 规则二：创建批次时解析成绝对时刻并存下来

UI 上用户选「近 30 天」（人就是这么想的），但**创建批次的瞬间**
就把它解析成 `windowFrom` / `windowTo` 两个绝对 timestamp 存进表里。
worker 与查询一律读这两个值，**不再重新解析相对表达**。

#### 为什么规则一不能替代规则二

规则一消掉了「跑批期间新执行涌入」这个主因，但相对表达仍有三个缺口：

| 缺口 | 后果 |
|---|---|
| **跨零点** | 批次 23:58 创建，`plannedCount` 按 `[7/9, 8/8)` 算；00:01 重新解析变成 `[7/10, 8/9)`，**左边界前移一天**。7/9 的执行已计入 planned 却掉出窗口 → `completedCount` 永远追不上，批次卡死在 RUNNING。**这是每天必然出现一次的窗口**，批次越长越容易撞上。 |
| **时区** | 「当天」是谁的当天？租户在纽约、库存 UTC，差 5 小时。相对表达把这个歧义留在运行期，每次解析都可能得到不同答案。 |
| **迟到写入** | `createdAt` 不必然等于落库时刻——异步 outbox、重试、时钟偏移，都可能让一条 `createdAt` 在昨天的记录今天才写进来。它会进窗口，但不在 `plannedCount` 里。 |

**更根本的理由**：窗口边界不只是执行时需要，**它是结果的一部分**。
用户三天后回看这个批次，「近 30 天」是相对于创建时还是查看时？
没有存下绝对时刻就无法回答，结果不可复现。
而 §1.1 的第一性约束要求用户能理解自己看的是什么总体——
「近 30 天」在三天后已经不指向同一个总体了。

固化的代价是两个 timestamp 列。收益是竞态、时区、可复现性一次性全解决。

#### 时区口径（写死，不留歧义）

「当天 00:00」按**租户时区**计算，存成 **UTC 绝对时刻**。
租户时区取自租户配置；未配置时回退 UTC 并在结果里标注口径。

理由：用户说「近 30 天」时想的是自己日历上的 30 天。
按 UTC 算会让纽约用户的窗口边界落在当地 19:00 或 20:00（随夏令时变），
既不直观也不稳定。本仓已有日历日 vs instant 的口径踩坑先例，此处一次写清。

#### 存储形态示例

```
用户选择：  最近一个月（租户时区 America/New_York，今天 2026-08-08）
      ↓ 创建批次瞬间解析
windowKind:     LAST_MONTH
windowLabel:    "最近一个月"          ← 与数字同屏显示的口径文案
windowTimezone: America/New_York
windowFrom:     2026-07-08T04:00:00Z  ← 纽约 7/8 00:00（自然月，非 30 天）
windowTo:       2026-08-08T04:00:00Z  ← 纽约 8/8 00:00（不含当天）
```

worker 扫的是 `createdAt >= windowFrom AND createdAt < windowTo`，
`windowTo` **左闭右开**——避免边界那一毫秒的执行被算两次或漏掉。

## 4. 护栏（不是可选项）

继承 0033 §4，并针对异步补充：

1. **全成功才出数**。`FAILED` 批次**不得**返回任何会被读成结论的数字字段——
   连 `partialCount` 都不给，因为它会诱导前端自行计算比率。
2. **失败要给原因分布**，不是一句「失败了」。用户需要知道是脏数据还是版本不兼容。
3. **租户隔离**：所有 batch 读写带 `eq(userId)`；拒答路径先校验归属再返回状态码，
   否则端点退化成「策略是否存在」的探针。
4. **并发闸门复用**：重跑走 `/evaluate-source`，已有 `PermitLease` 背压
   （见 aster-api #222）。批次 worker **不得**绕过它。
5. **模拟不计费**：复用已上线的 `?simulate=true`（HMAC 绑定），
   一次批次不该扣 N 次配额、不该写 N 条业务指标与审计事件。
6. **toolchain 漂移**：批次完成后若 `toolchainId` 已变，结果标记为
   `STALE` 并在 UI 上说明，而不是静默呈现。
7. **批次有过期**：`EXPIRED` 状态，避免无限堆积陈旧结果。

## 5. 分阶段交付

| 阶段 | 内容 | 判据 |
|---|---|---|
| **S1**（cloud） | `replay_batch` 表 + 领域模型 + 状态机单测 | 状态迁移穷举覆盖；非法迁移必须抛错 |
| **S2**（cloud） | 异步 worker + 全成功/任一失败两条路径 | **变异验证**：注入一条失败 → 整批必须 FAILED 且零数字 |
| **S3**（cloud） | REST：创建批次 / 查询进度 / 取结果 + **并发上限 entitlement** | 租户隔离、拒答不成探针、409/404 语义；并发超限 409 带当前批次 id。★`concurrentReplayBatches` 需 plan-gate 侧加字段——**外部依赖，见 §8**。测试须分别覆盖 free→**403**（无权益）与 pro 已有批次→**409**（并发超限），两者不可混为一谈 |
| **S4**（cloud） | 前端：窗口选择器（4 档 + 自定义）+ 进度条 + 结果/拒答两态 | 窗口口径与数字同屏；失败态显示原因分布；**进度条不得显示中间成功数**（§7.4）；未来日期前端 disable + 服务端独立拒绝；free 租户入口可见但禁用 + 升级引导（§7.5），禁用态**不得**给试用额度或样例数字 |
| **S4.5**（cloud） | 过期清理定时任务 | 30 天转 EXPIRED、清空聚合结果、保留元数据；**读路径不得有写副作用** |
| **S5** | 交叉审查 | **≥90 分方可合并**（0033 那版五轮未过 60） |

S0 性能实测已在 0033 §5.1 完成且**在本模型下依然有效**：
单条重跑 avg 1.35ms / max 5.44ms，200 条 270ms。
异步形态下这不再是硬约束（不受 HTTP 超时限制），
按此推算万条量级约 13 秒，完全可行。

## 6. 不做的事

- **不做部分成功估算**——违反 §1.1，是上一版的死因。
- **不落逐条 targetDecision**——PII 面与失效语义，0033 §3.2 的这条理由仍成立。
- **不做跨策略比较**——本 ADR 只解决同一策略的两个版本。
- **不复用已删除的前端面板**——原组件的 `?? 0` 兜底会把字段缺失渲染成 0，
  正是「拒答被读成结论」的典型。重建。

## 7. 已拍板（2026-08-08）

### 7.1 窗口档位

**预设**：最近一个月 / 一个季度 / 半年 / 一年。
**外加自定义**：任意起止日期。

★ **不能选未来**。校验放在**创建批次时**，不是前端 disable 就算数——
前端只是体验，服务端必须独立拒绝，否则 API 直连可绕过。

自定义窗口的服务端校验：

| 规则 | 拒绝理由 |
|---|---|
| `to > 当天00:00`（租户时区） | 未来窗口无数据，且会让 §3.3 的边界语义失效 |
| `from >= to` | 空窗口 |
| `from` 早于该策略最早执行 | 不拒绝，静默收敛到该策略最早执行时刻——用户要「全部」就是选一个足够早的 `from` |

预设档位同样按 §3.3 解析：右边界一律取**当天 00:00**（不含当天），
「一个月」= 自然月而非 30 天（用户说「一个月」想的是日历月）。

### 7.2 批次并发上限：按套餐（**这是计费维度，不只是技术限制**）

同一租户同时允许的 `PENDING`/`RUNNING` 批次数**由套餐决定**（见下表）。
达到上限时创建新批次 → **409**，附当前批次 id 与进度。

> **需更高并发 = 额外付费。**

#### 档位（已定）

| 套餐 | `concurrentReplayBatches` | 含义 |
|---|---|---|
| **free** | **0** | **完全不能用 What-If**——不是「只能跑一个」 |
| **pro** | 1 | 一次一个批次 |
| **enterprise** | 可自定义 | 按合同配置 |

★ **free = 0 把并发上限从「限流」变成了「功能开关」**。
这不只是数字差异——它意味着权限判定要在**创建批次的入口**就发生，
而不是等排队时才拒。实现上是同一个字段，语义上是两件事，
测试必须分别覆盖：free 租户 → 403（无权益）；pro 租户已有批次 → 409（并发超限）。
**两者状态码不同**，因为「你没这个功能」与「你现在不能再开一个」是不同的事。

#### 谁写入（已定）

**我方运营/客服在 plan-gate 侧配置，租户管理员只读。**
产品内**不建写入口**——权益变更走商务流程。

这带来两个简化：

- 不需要新建租户设置页，也不需要「合同上限从哪来」这个二级问题
- 不存在「管理员自助提权」的绕过面：唯一写入点在 plan-gate，天然受控

租户管理员（`Role.ADMIN`）可在设置页**查看**当前档位与已用批次数，
但看不到写入控件。这是有意的——只读也是一种明确的产品表达。

#### 实现链路

- 本仓已有 `PlanGateService.lookupPlan(tenantId)` → `PlanInfo`
  （字段：`plan` / `allowsApproval` / `maxTeamMembers` / `evaluationsLimit` / `apiCallsLimit`）
- 新增权益字段 `concurrentReplayBatches`

⚠️ **`PlanInfo` 是跨服务契约**（由 plan-gate 服务下发），不是本仓的枚举。
加字段涉及 plan-gate 侧同步，**S3 必须把这件事当独立前置项**，
不能等实现时才发现要改别人的服务。

**降级语义**：plan-gate 不可达时 `PlanInfo.failOpen()` 返回 pro 档。
并发上限**不适用 fail-open**——取不到权益时按 **0** 处理（fail-closed，即拒绝）。

★ 注意这里与 `failOpen()` 的 pro 档**刻意不一致**：
`failOpen()` 的设计意图是「服务抖动时不阻塞既有业务」，对读类操作合理；
但 What-If 批次是**新发起的、消耗计算资源的付费能力**，
fail-open 等于「plan-gate 一抖动，free 租户就能免费跑批」。
故此处显式覆盖为 0，并在日志里留痕（不是静默拒绝，运维要能查到原因）。

### 7.3 结果保留 30 天

`COMPLETED` / `FAILED` 批次保留 **30 天**，之后转 `EXPIRED`。

- `EXPIRED` 批次**保留元数据**（窗口口径、planned/completed、创建时间），
  **清空聚合结果**——用户能看到「我当时跑过这个」，但看不到过期数字。
- 理由：数字有时效性（策略/词汇/工具链都会变），留着陈旧数字比删掉更危险。
- 清理走定时任务；**不得**在读路径上做惰性删除（读操作不该有写副作用）。

### 7.4 万条以上：进度条

批次页面显示 `completedCount / plannedCount` 进度条。

- 前端轮询批次状态端点；**不做 WebSocket/SSE**（一个进度条不值得引入长连接）
- 轮询间隔随批次规模自适应：小批次 1s，万条以上 5s，避免打爆查询端点
- **进度条只反映进度，不预告结果**——不得显示「已成功 N 条」这类中间数字，
  否则用户会在批次跑完前自行推断结论，这正是 §1.1 要防的
- 万条按 S0 实测（1.35ms/条）约 13 秒；进度条主要服务于**更大规模**与**心理预期**

**不做**邮件通知——当前规模（万条 ~13 秒）不需要，属过度设计。
若将来出现十万条量级再议。

### 7.5 free 租户的呈现：入口可见但禁用 + 升级引导

免费租户**能看到** What-If 入口，点击提示「此功能需 Pro 及以上」并给升级路径。

理由：让用户知道有这个能力才会想升级。完全隐藏虽然界面更干净，
但失去转化机会——而 What-If 恰恰是能体现产品价值的功能。

★ **服务端仍硬拒（403），不靠前端隐藏**。
前端 disable 只是体验层；API 直连必须被独立拒绝。
这与 §7.1「未来日期」是同一条原则：**前端是提示，服务端是边界**。

★ 禁用态的文案**不得**暗示「跑一下试试就知道」——
不给试用额度、不给样例数字。否则 §1.1 的约束在营销路径上被绕过。

## 8. 外部依赖（阻塞 S3，不阻塞 S1/S2）

**`PlanInfo` 需新增 `concurrentReplayBatches` 字段**——由 plan-gate 服务下发，
不是本仓能单方面改的。

- 档位已定（§7.2）：free=0 / pro=1 / enterprise 按合同
- 写入方已定：我方运营/客服，租户管理员只读
- **仍需对接**：plan-gate 侧何时能加这个字段

**未接通前的临时形态**（可接受，但必须显式标注）：
本仓按 `plan` 字段自行映射（free→0 / pro→1 / enterprise→1），
代码中留 `// TODO(0034-§8)` 并在 §9 修订记录里注明。
⚠️ 临时形态下 **enterprise 拿不到自定义值**，只能按 1——
这是已知缺口，不是「先这样以后再说」的含糊处理。

- 2026-08-08：初稿。取代 0033 §3；采纳异步 ReplayBatch + 用户可选时间窗口
  （含全量选项）。用户决策：重跑失败一律 fail-closed 整批拒答。
- 2026-08-08：§3.3 改写。用户提出「『近 30 天』不含当天能否避免集合漂移」——
  方向正确且被采纳为**规则一**（右边界取当天 00:00 而非 `now()`，边界指向已封闭的
  过去，正在写入的数据天然在窗口外）。但它**不能替代固化**：跨零点会让左边界前移
  一天（每天必然出现一次的窗口，`completedCount` 永远追不上）、时区歧义留在运行期、
  迟到写入仍会漏出 `plannedCount`；更根本的是窗口边界是**结果的一部分**，
  不存绝对时刻则结果不可复现。故两条规则并存。同时写死时区口径（按租户时区算
  「当天」、存 UTC）与「全部」窗口的边界语义。
- 2026-08-08：§7 四条全部拍板（窗口档位 / 并发上限 / 保留时长 / 进度条）。
  ★ 并发上限=1 被识别为**计费维度而非技术常量**——必须走既有 entitlement
  链路（`PlanGateService` → `PlanInfo`），而 `PlanInfo` 是 **plan-gate 服务下发的
  跨服务契约**，加 `concurrentReplayBatches` 字段需对方配合。这是 S3 的**外部依赖**，
  已提为 §8.1，不能等实现时才发现。并发上限**不适用 fail-open**：
  取不到权益时按 1 处理，否则服务抖动等于免费开放付费权益。
  窗口档位改为「最近一个月/一个季度/半年/一年 + 自定义」，`ALL` 取消
  （「全部」= 自定义一个足够早的 from）；未来日期**服务端独立拒绝**，
  不依赖前端 disable。
- 2026-08-08：§7.2 档位与写入方拍板。free=0 / pro=1 / enterprise 可自定义；
  **我方运营/客服在 plan-gate 侧配置，租户管理员只读、产品内不建写入口**

  ★ fail-closed 值从 1 改为 **0** 并说明为何刻意与 `failOpen()` 的 pro 档不一致。
