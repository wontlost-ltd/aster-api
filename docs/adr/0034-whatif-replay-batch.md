# ADR 0034：What-If 重做——异步 ReplayBatch 模型

- 状态：**PROPOSED**（2026-08-08）
- 取代：[ADR 0033](0033-whatif-replay-correlation-model.md) 的 §3（按需同步重求值）
- 继承：0033 的 §2（能力已存在）、§3.1 的关联键洞见、§4 护栏、§5.1 S0 实测

---

## 0. 一句话

What-If 要回答「把策略从 v1 换成 v2，业务指标会怎样」。
重做的形态是：**用户显式选定时间窗口 → 窗口内全量执行异步重跑 → 全部成功才出数字，
任一条失败即整批拒答**。

---

## 1. 为什么重做：上一版死在哪

Phase 4 五轮评分 52 → 43 → 58 → 48 → 47，无收敛，第十二轮判定撤下。
**决定性的一条是选择偏差**，必须写清楚，否则重做会再踩：

上一版允许「200 条发起、30 条成功」就对这 30 条出完整业务数字。
但重跑失败**与输入、词汇、策略路径相关**——若 80% 因某类输入失败，
剩下 20% 就是被筛选过的子群，不是随机样本。据此算出的正面率与金额
可能方向对而幅度全错，甚至方向本身有偏。

**这不是加 caveat 能解决的**：它是用非随机样本冒充总体影响。
前几轮一直在修「数字算错了」，而真正的问题是「这批数字凭什么代表总体」。

### 1.1 本 ADR 的第一性约束

> **任何被呈现的数字，其样本必须是某个用户能理解的总体的全量，而非该总体的成功子集。**

下面所有设计都是这条约束的推论。若某个方案违反它，无论多方便都不采纳。

---

## 2. 决策：异步 ReplayBatch + 用户可选时间窗口

### 2.1 两条被否的替代方案

| 方案 | 否决理由 |
|---|---|
| **同步 + fail-closed**（0033 形态的修正版） | 消偏差有效，但「一条脏数据全废」在大策略上几乎必然触发——用户永远拿不到结果。且 HTTP 超时把样本上限锁死在几百条量级，业务价值受限。 |
| **同步 + 部分成功估算** | 即上一版。**违反 §1.1**，已被五轮审查证伪。 |

### 2.2 采纳形态

```
用户选定窗口（如「近 30 天」/「全部」）
        ↓
创建 ReplayBatch（PENDING）——记录窗口口径、base/target 版本、planned 总数
        ↓
异步 worker 逐条重跑（运行与查询分离，可跨请求、可重试）
        ↓
    ┌── 全部成功 → COMPLETED → 出数字
    └── 任一失败 → FAILED    → 拒答 + 报告失败原因分布
```

**时间窗口是显式口径，不是隐形抽样。**
UI 上必须写「本结果基于近 30 天全部 N 条可重跑执行」——
用户知道自己在看什么总体，这与「从 200 条里挑出成功的 30 条」有本质区别。

### 2.3 关联键（继承 0033 §3.1，不变）

关联键**不是 `executionId`**，而是「同一条 input」。
`Execution.id` 是主键、`policyVersion` 是普通列，同一 id 不可能同时属于两个版本，
跨版本交集**结构上恒为空**。所以对照只能来自**重跑**：

```
(sourceExecutionId → 用它的 input 在 targetVersion 上重跑得到的 decision)
```

## 3. 数据模型

### 3.1 ReplayBatch（新表）

| 字段 | 说明 |
|---|---|
| `id` | 批次主键 |
| `tenantId` / `userId` | **租户隔离必需**；所有读写一律带 `eq(userId)` |
| `policyId` | 被比较的策略 |
| `baseVersionId` / `targetVersionId` | 两个版本的行 id（不是版本号字符串） |
| `windowKind` | `LAST_N_DAYS` / `ALL`（显式口径，进 UI 文案）。★`ALL` 同样固化边界：`windowFrom` 为该策略最早执行时刻，`windowTo` 仍取当天 00:00——「全部」不等于「不设边界」 |
| `windowDays` | `LAST_N_DAYS` 时有效 |
| `windowFrom` / `windowTo` | **创建时固化的绝对时刻**，左闭右开；右边界取当天 00:00（不含当天）——见 §3.3 |
| `windowTimezone` | 解析「当天」所用的租户时区（如 `America/New_York`）；未配置时为 `UTC` 并需在结果里标注 |
| `plannedCount` | 窗口内可重跑执行总数，创建时确定 |
| `completedCount` / `failedCount` | 进度 |
| `status` | `PENDING` / `RUNNING` / `COMPLETED` / `FAILED` / `EXPIRED` |
| `failureReasons` | 失败原因分布（JSON），拒答时回报给用户 |
| `toolchainId` | 创建时的工具链身份，用于判断结果是否仍可信 |
| `createdAt` / `finishedAt` | |

### 3.2 为什么这次要落表（推翻 0033 §3.2）

0033 拒绝落 `ReplayComparison` 表，理由是失效语义复杂、口径不如重跑诚实、零 schema 变更。
**那些理由在同步模型下成立，在异步模型下不成立**——必须诚实说明这个反转：

- 异步的本质就是**运行与查询分离**，中间状态**必须**可持久化，否则进程重启即丢失。
- 落的不是「预计算对照表」，而是**一次批次运行的账本**。它不试图长期有效，
  只记录「这一次、在这个窗口、用这个工具链跑出了什么」。
- 失效语义因此简单：批次是**不可变快照**，不需要失效重算；
  策略源码变了就是新批次，旧批次仍如实反映它当时跑的东西。

**注意**：只落 batch 元数据与聚合结果，**不落逐条 targetDecision**——
那才是 0033 真正想避免的东西（PII 面扩大 + 失效语义复杂）。

### 3.3 窗口边界：右边界取当天 00:00，并固化成绝对时刻

**两条规则，缺一不可。**

#### 规则一：右边界是「当天 00:00」，不是 `now()`

窗口取 `[当天00:00 - N天, 当天00:00)`——**不含当天**。
右边界指向一个已经封闭的过去，正在写入的数据天然落在窗口外。

这比取 `now()` 更稳：`now()` 会把边界切在数据正在写入的位置，
虽然固化后不再漂移，但「边界那一刻的执行算不算」本身就是个模糊地带
（写入时刻 vs `createdAt` 时刻、事务可见性）。取 00:00 让这个问题消失。

代价是**今天的执行永远看不到**。这是可接受的——What-If 回答的是
「换版本会怎样」，一天的延迟不影响判断；而边界干净带来的可复现性更值钱。

#### 规则二：创建批次时解析成绝对时刻并存下来

UI 上用户选「近 30 天」（人就是这么想的），但**创建批次的瞬间**
就把它解析成 `windowFrom` / `windowTo` 两个绝对 timestamp 存进表里。
worker 与查询一律读这两个值，**不再重新解析相对表达**。

#### 为什么规则一不能替代规则二

规则一消掉了「跑批期间新执行涌入」这个主因，但相对表达仍有三个缺口：

| 缺口 | 后果 |
|---|---|
| **跨零点** | 批次 23:58 创建，`plannedCount` 按 `[7/9, 8/8)` 算；00:01 重新解析变成 `[7/10, 8/9)`，**左边界前移一天**。7/9 的执行已计入 planned 却掉出窗口 → `completedCount` 永远追不上，批次卡死在 RUNNING。**这是每天必然出现一次的窗口**，批次越长越容易撞上。 |
| **时区** | 「当天」是谁的当天？租户在纽约、库存 UTC，差 5 小时。相对表达把这个歧义留在运行期，每次解析都可能得到不同答案。 |
| **迟到写入** | `createdAt` 不必然等于落库时刻——异步 outbox、重试、时钟偏移，都可能让一条 `createdAt` 在昨天的记录今天才写进来。它会进窗口，但不在 `plannedCount` 里。 |

**更根本的理由**：窗口边界不只是执行时需要，**它是结果的一部分**。
用户三天后回看这个批次，「近 30 天」是相对于创建时还是查看时？
没有存下绝对时刻就无法回答，结果不可复现。
而 §1.1 的第一性约束要求用户能理解自己看的是什么总体——
「近 30 天」在三天后已经不指向同一个总体了。

固化的代价是两个 timestamp 列。收益是竞态、时区、可复现性一次性全解决。

#### 时区口径（写死，不留歧义）

「当天 00:00」按**租户时区**计算，存成 **UTC 绝对时刻**。
租户时区取自租户配置；未配置时回退 UTC 并在结果里标注口径。

理由：用户说「近 30 天」时想的是自己日历上的 30 天。
按 UTC 算会让纽约用户的窗口边界落在当地 19:00 或 20:00（随夏令时变），
既不直观也不稳定。本仓已有日历日 vs instant 的口径踩坑先例，此处一次写清。

#### 存储形态示例

```
用户选择：  近 30 天（租户时区 America/New_York，今天 2026-08-08）
      ↓ 创建批次瞬间解析
windowKind: LAST_N_DAYS
windowDays: 30
windowFrom: 2026-07-09T04:00:00Z   ← 纽约 7/9 00:00
windowTo:   2026-08-08T04:00:00Z   ← 纽约 8/8 00:00（不含当天）
```

worker 扫的是 `createdAt >= windowFrom AND createdAt < windowTo`，
`windowTo` **左闭右开**——避免边界那一毫秒的执行被算两次或漏掉。

## 4. 护栏（不是可选项）

继承 0033 §4，并针对异步补充：

1. **全成功才出数**。`FAILED` 批次**不得**返回任何会被读成结论的数字字段——
   连 `partialCount` 都不给，因为它会诱导前端自行计算比率。
2. **失败要给原因分布**，不是一句「失败了」。用户需要知道是脏数据还是版本不兼容。
3. **租户隔离**：所有 batch 读写带 `eq(userId)`；拒答路径先校验归属再返回状态码，
   否则端点退化成「策略是否存在」的探针。
4. **并发闸门复用**：重跑走 `/evaluate-source`，已有 `PermitLease` 背压
   （见 aster-api #222）。批次 worker **不得**绕过它。
5. **模拟不计费**：复用已上线的 `?simulate=true`（HMAC 绑定），
   一次批次不该扣 N 次配额、不该写 N 条业务指标与审计事件。
6. **toolchain 漂移**：批次完成后若 `toolchainId` 已变，结果标记为
   `STALE` 并在 UI 上说明，而不是静默呈现。
7. **批次有过期**：`EXPIRED` 状态，避免无限堆积陈旧结果。

## 5. 分阶段交付

| 阶段 | 内容 | 判据 |
|---|---|---|
| **S1** | `ReplayBatch` 表 + 领域模型 + 状态机单测 | 状态迁移穷举覆盖；非法迁移必须抛错 |
| **S2** | 异步 worker + 全成功/任一失败两条路径 | **变异验证**：注入一条失败 → 整批必须 FAILED 且零数字 |
| **S3** | REST：创建批次 / 查询进度 / 取结果 | 租户隔离、拒答不成探针、409/404 语义 |
| **S4** | 前端：窗口选择器 + 进度 + 结果/拒答两态 | 窗口口径与数字同屏；失败态显示原因分布 |
| **S5** | 交叉审查 | **≥90 分方可合并**（0033 那版五轮未过 60） |

S0 性能实测已在 0033 §5.1 完成且**在本模型下依然有效**：
单条重跑 avg 1.35ms / max 5.44ms，200 条 270ms。
异步形态下这不再是硬约束（不受 HTTP 超时限制），
按此推算万条量级约 13 秒，完全可行。

## 6. 不做的事

- **不做部分成功估算**——违反 §1.1，是上一版的死因。
- **不落逐条 targetDecision**——PII 面与失效语义，0033 §3.2 的这条理由仍成立。
- **不做跨策略比较**——本 ADR 只解决同一策略的两个版本。
- **不复用已删除的前端面板**——原组件的 `?? 0` 兜底会把字段缺失渲染成 0，
  正是「拒答被读成结论」的典型。重建。

## 7. 待拍板

1. **窗口预设档位**：`近 7 天 / 近 30 天 / 近 90 天 / 全部` 是否够用？
2. **批次并发上限**：同一租户同时允许几个 RUNNING 批次？（防自我 DoS）
3. **过期策略**：批次结果保留多久？
4. **万条以上的超大策略**：是否需要进度条以外的体验（如邮件通知）？

  （含全量选项）。用户决策：重跑失败一律 fail-closed 整批拒答。
- 2026-08-08：§3.3 改写。用户提出「『近 30 天』不含当天能否避免集合漂移」——
  方向正确且被采纳为**规则一**（右边界取当天 00:00 而非 `now()`，边界指向已封闭的
  过去，正在写入的数据天然在窗口外）。但它**不能替代固化**：跨零点会让左边界前移

  不存绝对时刻则结果不可复现。故两条规则并存。同时写死时区口径（按租户时区算
  「当天」、存 UTC）与 `ALL` 窗口的边界语义。
