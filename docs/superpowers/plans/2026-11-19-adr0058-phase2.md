# ADR 0058 阶段 2（策略的 LayoutMap）实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让有「结构化编写」能力的作者给小型策略的版本附一份 LayoutMap（显示排版），保存时机械校验「编译的就是 canonical」；任何能读版本的人都能只读查看 display，但评审、审批、对比一律 canonical 优先；演示与 aster-dev 改用包导出，删除副本。

**Architecture:** cloud 新增一张只插入的 `PolicyVersionLayout` 表（迁移单独先行）。`createVersion` 是三态规则（省略 / `null` / 对象）与校验的唯一实现点，校验直接调用已发布的 `@aster-cloud/aster-lang-ts@3.3.0` 的 `./layout`；layout **不进** `computeSourceEnvelope`。读取只有一个入口 `loadVersionLayout`，每次复验哈希与往返。编辑器保持 Monaco 为 canonical 编辑器，在旁边渲染 display 窗格，span 编辑只做「切分 + 改 display」。

**Tech Stack:** cloud：Next.js（Cloudflare Workers）、Drizzle + Postgres、vitest（unit / integration PG）、Playwright、next-intl。aster-dev：Next.js + vitest。依赖：`@aster-cloud/aster-lang-ts` **3.3.0（已发布，不发新版）**。

**Spec:** `docs/adr/0058-structured-authoring-capability-and-policy-layout.md`（ACCEPTED 2026-11-16）。本计划实施 ADR §7 与 §9.2（§7.8 的 decision trace 投影除外，见裁决 R14）；对应 wontlost-ltd/aster-cloud#794（伞形 #791）。阶段 1 计划：`docs/superpowers/plans/2026-11-16-adr0058-phase1.md`。

## Global Constraints

- **envelope 两侧逐字节不变**：`computeSourceEnvelope` 的签名、段序、`envelope-vectors.json` 与 Java `PolicyVersion.computeSourceEnvelope` 都不改；layout 不进任何哈希链（`sourceHash`、`prevHash`、envelope）。**aster-api 无代码改动**（ADR §5.3、§7.2；见裁决 R1）。
- **不发版**：只用已发布的 `@aster-cloud/aster-lang-ts@3.3.0`；本计划没有 ts 或引擎任务，没有车次门（eco-1.0.51 继续冻结到 #791 完成）。
- 迁移先行：`drizzle/*.sql` 只出现在只含迁移的 PR（`schema.ts`、`drizzle/meta/`、`src/__tests__/` 可同 PR）；不用 `migration-and-code` 标签；迁移在生产确认应用后才合使用它的代码 PR。
- 表 `PolicyVersionLayout`：每版本至多一行；**不可 UPDATE、不可直接 DELETE**，只随父 `PolicyVersion` 级联删除（R8）；`formatVersion = 1`；`layout` 为 `serializeLayout` 的输出（text，不用 jsonb）；`layoutSha256` = `sha256(layout 的 UTF-8)`、`sourceSha256` = `sha256(版本源码的 UTF-8)`，均为 64 位小写十六进制、无前缀。
- 规模上限一律取包的 `LAYOUT_LIMITS`（12288 / 200 / 400 / 49152 / 24576 / 256），cloud 不另写常量。
- 错误码（JSON `{ error, code, offset?, limit? }`）：400 `layout_invalid_format`、`layout_too_large`、`layout_roundtrip_mismatch`、`layout_structural_hides_value`、`layout_content_parity`；403 `structured_authoring_required`。下文称这六个为「layout 错误码」。
- 三态（请求体 `layout` 字段）：省略 → 沿用规则（ADR §7.5 第一行）；`null` → 不带；对象 → 必须有权且全量校验。响应字段 `layoutDropped: boolean`。
- 门禁：layout 写入与编辑器的排版入口按 `resolveEntitlement(userId, 'structured_authoring', { teamId: policy.teamId })` 判定；**只读查看不设门**（版本详情 / 审批、策略详情、对比、复核）；语言特性与编译、执行路径不变。
- 下游不读 layout：执行、证据、Cedar 导出、包导出、What-If、回放、Guard 部署、版本列表不得引用 `@/lib/policy-layout/store`。
- 偏移一律 UTF-16 code unit，换行不归一化（ADR §7.8）；行列 1 起始。
- 能力为假时编辑器 DOM 与今天逐字节一致；没有 layout 的版本，本计划改动的每个只读视图（版本详情、策略详情源码卡片、版本对比、复核面板）DOM 与今天逐字节一致，各有快照（T7、T8）。
- 客户端组件只从 `@aster-cloud/aster-lang-ts/layout` 或 `/browser` 导入（不导入主入口，见 `policy-review-panel.tsx:17-21` 的 `node:crypto` 教训）；`src/lib/policy-layout/store.ts`、`hash.ts` 只在服务端使用。
- 新文案进 `src/i18n/demo-supplement.ts`（en / zh / de / hi）。代码注释用简体中文。
- 提交信息结尾 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`；PR 正文结尾 `🤖 Generated with [Claude Code](https://claude.com/claude-code)`。

## Review Focus

1. **只改别名或 locale、省略 layout**：沿用前必须用**新版本**的 aliasSet / locale 重跑校验。旧版本结构 span 里的词若因别名被删而变回标识符，新版本不得沿用，响应 `layoutDropped: true`（T4）。
2. **只改 layout 的 PUT**：源码与别名不变、提交的 layout 与活跃版本不同 → 建新版本；与活跃版本完全相同（`layoutSha256` 相等）→ 不建版本（T5）。
3. **存量行不一致**（直接改库的 `layout`、resolver 迁移或改库造成的 `content` 变化）：读接口 200 + `status: 'inconsistent'`，视图只显示 canonical 与提示，编辑器不加载，下次保存不沿用且 `layoutDropped: true`（T3、T4、T6、T7）。
4. **无权队友（或套餐降级后的作者）编辑带 layout 的团队策略**：保存成功（不 403），新版本无 layout，`layoutDropped: true`，保存前有提示；旧版本的 display 仍可只读查看（T4、T11、T12）。
5. **源码含代理对（emoji）与 `\r\n`**：行列 ↔ 偏移换算、区间投影与 span 切分都按 UTF-16，切分不得落在代理对中间（T9）。

| # | 问题 | 裁决 | 理由 |
|---|---|---|---|
| R1 | aster-api 是否要改 | **不改**。仅在 T4 的验证步骤确认 aster-api `src/` 与两侧 `envelope-vectors.json` 无差异 | ADR §5.3、§7.2；aster-api 的版本表独立（见现状），不读 layout |
| R2 | ADR §4.9 的「既有 `policy.version.create` 审计」并不存在 | 扩展既有安全事件 `VERSION_CREATED` 的 `details`：加 `layoutSha256`（无则 `null`）与 `layoutDropped`；不新造 `AuditLog` 动作 | 建版本今天只写这一条事件（`version-manager.ts:550-561`）；新增动作会让同一事实落两处 |
| R3 | 第四条建版本路径 `POST /api/teams/[teamId]/policies` | 不接受 layout：忽略请求体的 `layout`（与它今天忽略 `aliasSet`、`locale` 一致），新版本无 layout；以测试钉住 | 它是新建团队策略的 API，没有上一版本可沿用，编辑器不调用它 |
| R4 | 只改 layout 是否建新版本 | 是（ADR §7.2「想换 layout 就建新版本」）。PUT 的 `layoutChanged` = 提交对象的 `layoutSha256` ≠ 活跃版本的，或提交 `null` 而活跃版本有 layout；它与 content / 别名变化同样触发新版本 | 与 alias-only 变更建版本的先例一致（`[id]/route.ts:208-212`） |
| R5 | 「上一活跃版本」指哪一行 | `PolicyVersion.version = Policy.version` 的那一行（与 aliasSet 沿用同口径），在 `createVersion` 的事务内、链尾锁之后读取 | 与 `[id]/route.ts:182-189` 同口径；在锁内读避免并发保存各自沿用 |
| R6 | 沿用是否重跑校验 | 重跑 `validatePolicyLayout`（新源码、新 locale、新 aliasSet），任一失败即不沿用并 `layoutDropped: true` | Review Focus 1；ADR §7.5 只写了往返相等，但 hides_value 依赖别名 |
| R7 | 校验所用词法表 | `getLexicon(locale)` + 该版本生效的 aliasSet；不并入领域词汇 | ADR §7.5「版本的 locale 词法表（含冻结的关键词别名）」；词汇术语本身是标识符，必须在内容 span |
| R8 | 「只插入，不更新、不删除」如何在库里保证 | 迁移内加两个 trigger：`BEFORE UPDATE` 一律拒绝；`BEFORE DELETE` 只在父 `PolicyVersion` 行已不存在时放行（`IF EXISTS (SELECT 1 FROM "PolicyVersion" WHERE id = OLD."policyVersionId") THEN RAISE …`）。外键级联删除由父表的 RI 触发器在父行删除**之后**执行，此时父行已不可见，因而放行；对子表的直接 DELETE 父行仍在，因而拒绝。两种情形都有集成测试 | ADR §7.2；0037 有 append-only trigger 先例；不依赖 `pg_trigger_depth()` 这类隐式语义 |
| R9 | `createdBy` 是否加 FK | 不加，普通 text，与 `PolicyVersion.createdBy`（`schema.ts:734`）一致 | 用户硬删除不应删除版本的显示层 |
| R10 | 读取用哪个连接 | 普通 `db`（与版本读取一致），不用 `freshDb` | 行不可变；新版本 id 首次查询不会命中旧缓存 |
| R11 | 编辑器形态 | Monaco 仍是 canonical 编辑器；display 是 Monaco 左侧的只读 React 窗格（#794：display 在左、canonical 在右）；排版操作在侧栏新标签 `layout`（rail 入口） | 不重造第二个编辑器；ADR §7.4 只允许在 canonical 上切分 |
| R12 | 源码改了以后旧 layout 怎么办 | 不自动重排（YAGNI）。编辑器显示「排版已失效」并提供「从恒等排版重新开始」「移除排版」；保存时按三态处理 | ADR §7.1：源码一变旧 layout 自然失效；自动对齐有歧义（§7.4 否决理由同） |
| R13 | 编辑器怎样把 layout 交给保存 | 不进 `PolicyDraftFields`（不改 localStorage 草稿 schema）；经 `PolicySaveContext.layout`（`undefined` = 省略）传给页面的保存函数 | 草稿 schema 升级会牵动草稿恢复逻辑，而未保存的排版丢了可以重做 |
| R14 | decision trace 的位置映射（ADR §7.8） | **本阶段只交付诊断投影；trace 投影列为有前提的延期项**。前提：decision trace 带上源码 span（ADR 0032，目前 PROPOSED；cloud `DecisionTrace` 与 Java `DecisionTrace` 都没有位置字段，见现状）。延期项的验收条件写死在此：届时 trace 面板对附 layout 的版本，用 T9 的 `projectCanonicalRange` 把每个步骤的 canonical span 投到 display 并在 `LayoutDisplayView` 高亮，测试覆盖内容 span 与结构 span 各一例。完成本计划后在 #794 留言登记该延期项并链接 ADR 0032 | 今天没有可投影的数据；投影函数本阶段已交付并测过，trace 接入只差数据 |
