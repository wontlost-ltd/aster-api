## Global Constraints

- **冻结**：aster-api main 在 eco-1.0.49 列车期间冻结；本计划不改 aster-api 代码。引擎仓 PR 可评审，列车结束前不合并；全部 PR 为 draft。
- **许可证**：aster-lang-ts `package.json` 的 `license` 字段**不改**（ADR §12.1a L1 待用户裁决，只阻塞 P3）；P1 不分发捆绑运行时的包，Release 资产照常发布。
- **版本下限**：Node `>=24.0.0`；Java 25（工具链与运行时）。
- **格式标识**：`format` = `"aster-policy-package"`，`formatVersion` = `"1.0"`；CLI 只接受主版本 `1` 且次版本 ≤ `0`。
- **CLI 名称**：Node 为 `@aster-cloud/aster-lang-ts` 既有 bin `aster`；JVM 为 `java -jar aster-cli-<ver>.jar`；子命令 `compile`、`run`、`verify`、`inspect`、`version`，两侧同名同义。
- **退出码**：0 成功；1 `EVAL_ERROR`；2 `INPUT_INVALID`、`ENTRY_NOT_FOUND`、`USAGE`；3 `PKG_INTEGRITY`、`PKG_SIGNATURE`、`PKG_UNSIGNED`、`PKG_UNTRUSTED_KID`；4 `PKG_INVALID_MANIFEST`、`PKG_UNSUPPORTED_FORMAT`、`PKG_UNSUPPORTED_IR`、`PKG_IR_DRIFT`、`COMPILE_ERROR`（仅 `compile` 子命令编译 `.aster` 失败；`run` 的 B 包本地编译失败一律报 `PKG_IR_DRIFT`，message 带编译诊断）；5 `TIMEOUT`、`RESOURCE_EXHAUSTED`。两侧共用这张表（`conformance/package-v1/exit-codes.json`）。
- **`run` 信封**（stdout 一行规范 JSON + `\n`）：`{"ok":true,"value":V,"meta":M}` 或 `{"ok":false,"error":{"code":C,"message":S},"meta":M}`；`M` 恒含 `signed`（bool）、`entry`（string\|null）、`coreIrSha256`（string\|null）、`engine`（`"aster-lang-ts-interpreter"` \| `"aster-lang-truffle"`）、`cliVersion`、`irRecompiled`（bool）。包在取得 IR 之前就失败时 `entry` / `coreIrSha256` 为 `null`。诊断只写 stderr。`verify` / `inspect` / `version` 的 stdout 同样是一行规范 JSON。
- **值的字节形态**（P0 结果 §3 修订）：`V` = 求值结果按 aster-api `/evaluate-json` 的 `result` 同一 JSON 树，再经「值规范 JSON」序列化（键码点升序、无空白、整数含 Long 精确十进制、非整数 Double 按 RFC 8785 §3.2.2.3）；**不用**空 TypeContext 的 ts `canonicalJson` / core `CanonicalJson.canonicalJson`（二者拒绝 Double 与超安全整数）。逐类型映射见 P0 结果 §3，T1 写进 `conformance/package-v1/VALUE-FORMS.md` 与 `vectors/value-json.json`。
- **超时与上限**：`--timeout` 缺省 `5s`（接受 `<n>ms` / `<n>s`，上限 `300s`）；Node `maxSteps = Number.MAX_SAFE_INTEGER`、`maxCallDepth = 10000`，求值 Worker 以 `resourceLimits: { stackSizeMb: 32 }` 启动（P0 结果 §2）；JVM 在缺省线程栈上求值，不调 `-Xss`。
- **IR 漂移**（P0 结果 §4 / 修订 A2）：B 的本地 IR 去掉 `origin.start.col` / `origin.end.col` 后的规范字节 SHA-256 ≠ `coreIr.positionFreeSha256` → `PKG_IR_DRIFT`，两个 CLI 用同一判据；**没有**绕过参数。`coreIr.sha256` 仍是平台 IR 的精确字节哈希，进 `meta.coreIrSha256`。
- **签名**：被签字节 = `manifest.json` 文件字节本身，且必须等于对其解析结果做规范 JSON 后的 UTF-8 字节（否则 `PKG_INVALID_MANIFEST`）；`sig` = 64 字节 Ed25519 签名 base64url 无填充；`manifest.sig.json` = `{"alg":"Ed25519","issuer":…,"kid":…,"sig":…}`。manifest schema 只允许 ASCII 键、字符串、整数、布尔、null、数组、对象，此域内规范 JSON 与 RFC 8785 字节相同（T1 向量对照 aster-guard `jcs.ts` 证明）。
- **信任锚**：CLI 内置 `export-jwks.json`，P1 为 `{"keys":[]}`（导出密钥在 P2 创建）；`--pubkey <file>`（32 字节 raw 公钥的 base64url 文本，或 JWK JSON）与 `--jwks <file|url>` 覆盖内置锚。无签名文件 → `PKG_UNSIGNED`，除非 `--allow-unsigned`（此时 `meta.signed=false`）。
- **网络**：只有 `--jwks <url>` 联网（https，10 s 超时）；其余一律不联网。
- **JVM 沙箱**：逐项复刻 `TrufflePolicyRuntime.newPooledContext()`（aster-api `src/main/java/io/aster/policy/runtime/TrufflePolicyRuntime.java`）：`allowHostAccess(HostAccess.newBuilder(HostAccess.EXPLICIT).allowArrayAccess(true).allowListAccess(true).allowMapAccess(true).build())`（入参以 host Map / List 传入，必须可读）、`allowIO(IOAccess.NONE)`、`allowNativeAccess(false)`、`allowHostClassLookup(name -> false)`、`allowPolyglotAccess(PolyglotAccess.NONE)`、`allowCreateProcess(false)`、`allowCreateThread(false)`（生产为缺省 false，CLI 显式写出）、`resourceLimits(statementLimit 10_000_000)`；共享 `Engine` 设 `engine.WarnInterpreterOnly=false`。这些值集中在 T7 的 `SandboxPolicy` 记录里，构建 Context 只读它。
- **路径规则**：`files[].path` 匹配 `^[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*$`，不得含 `..` 段；包内除 `manifest.json`、`manifest.sig.json`、`SHA256SUMS` 外不得有 `files[]` 之外的文件；不跟随符号链接。包可以是目录或 `.zip`（zip 条目名同样受此规则约束）。

## Review Focus

1. **同一包、两个 CLI、stdout 在「平台字段归一」后必须逐字节相同**——包括失败信封（同一 `code`、同一 `meta`），不只是成功值。`meta.engine` 与 `meta.cliVersion` 按定义两侧不同，比较前把这两个值分别替换为字面量 `"<ENGINE>"`、`"<CLI_VERSION>"`（规范 JSON 中二者都是字符串值，替换不改变其余字节）；`version` 子命令的 stdout 不参与跨 CLI 比较。T11 的门覆盖每个黄金包的每个 case。
2. **被篡改的包**：改载荷任一字节、改 manifest 任一字节、删签名、换签名、加多余文件、zip 条目含 `../`、manifest 键重排（非规范字节）——都必须在求值之前以退出码 3 / 4 失败。T1 的篡改夹具逐条覆盖，T2 / T8 共用。
3. **死循环与深递归**：指数分支递归的策略在 `--timeout 1s` 下必须在 ≈1 s 内以 `TIMEOUT` 退出（Node 由 Worker `terminate()`，JVM 由 `close(true)`），进程不得挂住；深递归 Node 报 `RESOURCE_EXHAUSTED` 而不是 `EVAL_ERROR`。T4、T8 各有测试。
4. **输入边界**：缺参数、多余键、类型错、Decimal 以 JSON 数字给出、非对象顶层、空 stdin——统一 `INPUT_INVALID`（退出码 2），两侧消息码相同。T1 夹具 `inputs-invalid/`。
5. **B 包本地编译与平台不一致**：本地 locales / CLI 版本不同导致 IR 字节不同 → `PKG_IR_DRIFT`，绝不求值；`aster compile <pkg> --out` 能取出本地 IR 供排查。T3、T8 测试用一个故意改了 `coreIr.positionFreeSha256` 并重新签名的夹具（修订 A2）。

### 1. T0.1 JVM fat jar 在 stock JRE 上运行

**决策门结论：T9 从 CLI 运行时闭包排除 `io.quarkus`，并同时排除 `org.antlr:antlr4`（ANTLR 工具链）与 `com.ibm.icu`；jre-a 预算定为 18 MiB。**

做法：spike 分支给 truffle 加 `com.gradleup.shadow` 9.2.2、`mergeServiceFiles()`，`Main-Class` 指向 spike 入口 `aster.truffle.spike.StockJreSpike`（按 aster-api `TrufflePolicyRuntime` 的生产沙箱逐项建 Context，共享 Engine，`--timeout-ms` 时用调度线程到点 `close(true)`）；`-PexcludeQuarkus=true` 加 `configurations.runtimeClasspath { exclude(group = "io.quarkus") }`，`-PexcludeAntlrTool=true` 加 `exclude(group = "org.antlr", module = "antlr4")` 与 `exclude(group = "com.ibm.icu")`，`-PwithPicocli=true` 加 `info.picocli:picocli:4.7.7` 估算 CLI 增量。IR 是 ts 3.2.0 `compile(test_life.aster).coreJson`（147 015 字节）。

| 变体 | jar 字节 | MiB |
|---|---:|---:|
| 全部依赖 | 56 766 399 | 54.14 |
| 排除 quarkus | 28 284 190 | 26.97 |
| 排除 ANTLR 工具链（保留 quarkus） | 40 483 417 | 38.61 |
| 排除 quarkus + ANTLR 工具链 | 12 001 208 | 11.45 |
| 同上 + picocli 4.7.7（CLI 估算值） | 12 417 699 | 11.84 |

- **quarkus 引用**：`grep -rn io.quarkus aster-lang-truffle/src/main/java` 无结果。truffle 只经 aster-lang-runtime 间接带入 quarkus：runtime 中引用 quarkus / jakarta 的只有 `io.aster.workflow.IdempotencyKeyManager` 与 `aster.runtime.workflow.InMemoryWorkflowRuntime`（排除后 jar 内对全部 `.class` 做字节检索确认：除这两个类自身外没有任何类引用它们，truffle 只用 `DeterminismContext`、`WorkflowEvent`、`EventStore`，三者不依赖 quarkus）。runtime jar 内自带的 `io/quarkus/runtime/graal/*Accessor`（GraalVM 替换类）留在 jar 里，无人加载，不影响运行。
- **ANTLR 工具链泄漏（新发现）**：aster-lang-core 用 Gradle `antlr` 插件，`antlr("org.antlr:antlr4:4.13.1")` 经插件把 `api` 扩展到 `antlr` 配置，导致已发布 POM 把 ANTLR 工具（antlr4 tool、ST4、antlr3 runtime、icu4j 72.1 共约 16 MiB，其中 icu4j 13.5 MB）列为运行时依赖。core / truffle / locales 主代码只 import `org.antlr.v4.runtime.*`。排除后 CNL 编译路径照常可用（同一 jar 直接喂 `test_life.aster` 源码，`CnlCompiler` → 结果 `321`）。根治应在 core 构建里断开 `api` 对 `antlr` 的继承（另开 core issue；对 aster-api 镜像同样省 16 MiB），CLI 不等它，先在 T9 排除。
- **fallback 警告原文**（`--warn`，即不设 `engine.WarnInterpreterOnly`）：`[engine] WARNING: The polyglot engine uses a fallback runtime that does not support runtime compilation to native code. … The following cause was found: JVMCI is required to enable optimizations. Pass -XX:+EnableJVMCI …`。Engine 设 `engine.WarnInterpreterOnly=false` 后消失（与 aster-api 共享 Engine 配置相同）。
- **其他 stderr**：JDK 25 对 Truffle 的 `sun.misc.Unsafe::objectFieldOffset` 与 `System::load`（受限方法）各打一段 `WARNING:`；排除 quarkus 后另有 `SLF4J(W): No SLF4J providers were found`（networknt 经 slf4j-api 打日志）。三者都只写 stderr，stdout 只有结果（`2>/dev/null` 后 stdout 恰为 `321`）。T9 处理：manifest 加 `Enable-Native-Access: ALL-UNNAMED`（消掉受限方法警告）；运行时加 `org.slf4j:slf4j-nop`（消掉 SLF4J 警告）；Unsafe 警告无法从 jar 内关闭，README 说明可用 `--sun-misc-unsafe-memory-access=allow`。
- **冷启动**（容器内 `java -jar … test_life.canon.json 1 40 20`，进程墙钟）：全依赖 jar 中位数 **946.5 ms**（898–1003）；排除 quarkus + ANTLR 工具链 **878 ms**（839–932）。进程内分解（后者）：JVM 启动到 main 26 ms，建 Engine 296 ms，首次求值（建 Context + 解析 IR + 执行）562 ms。
- **单次求值**（同一进程、共享 Engine、每次新建 Context，10 次）：首次 562 ms，其后 32.7 / 29.3 / 32.2 / 25.6 / 20.6 / 12.5 / 10.8 / 11.9 / 10.8 ms，**中位数 25.6 ms**（全依赖 jar 29.0 ms）。CLI 每次进程只求值一次，用户感知的是冷启动 ≈ 0.9 s。
- **超时与深递归（顺带验证 T7 的机制）**：指数分支递归 `spin(60)` 在 `close(true)` 1000 ms 看门狗下 1056 ms 返回 `PolyglotException cancelled=true`，进程墙钟 1368 ms，进程正常退出。线性递归 `deep(n)` 在默认线程栈下 n=1000 成功、n=2000 已 `resourceExhausted=true`（`Resource exhausted: Stack overflow`）；`-Xss8m` 下 n=20 000 仍溢出。
- **预算**：`ceil(11.84 MiB × 1.5) = 18 MiB`。

### 3. T0.3 值形态与输入约定

**决策门结论：值的字节形态不能用空 TypeContext 的 `canonicalJson`（Double 与超安全整数会直接抛错），改由两侧各实现一份「值规范 JSON」序列化器（规则见下）；与 `/evaluate-json` 的承诺从「逐字节相同」改为「JSON 树相等」；输入约定「`--input` 为按形参名的对象，按 IR 形参顺序转位置实参」与平台结果相同，确认采用，并补三条输入规则。**

做法：`aster-lang-test/scripts/spike-value-forms.mjs` 遍历 `corpus/tier1-parity/manifest.json` 中有 golden 的 241 个样本、960 个 case（含 de / zh / hi 词汇样本）。ts：`compile`（样本词法表 + 词汇）→ `readCoreIr` → `evaluate(…, { maxSteps: Number.MAX_SAFE_INTEGER })` → `JSON.parse(serializeGuestValue(value))`。平台：本地 aster-api `POST /api/v1/policies/evaluate-json`（`X-Tenant-Id: p0`、`X-User-Role: ADMIN`，apikey 校验关闭），policy 为同一份 IR（该端点不接收函数名，多 Rule 模块须给目标 Func 加 `@entry`，见下），context 分别给位置数组与按形参名的对象。另用 `spike-p0/t03-extra-probes.mjs` 补语料没覆盖到的 Map 输出、Long、Map / List / Double 入参、Decimal 字面量、Ok、None。

结果：960 case 中 943 树相同、9 个 `expectError` 两侧都失败、8 个不同（7 个 Enum，1 个是测量工具的产物，见「入口选择」）。

| 值类别 | case 数 | 平台 `result` 树形（规范） | ts `serializeGuestValue` | ts 侧映射 |
|---|---:|---|---|---|
| Int | 440 | JSON 整数 | 同 | 无 |
| Long | 探针 | JSON 整数（`12000000000000000`，超出 2⁵³ 也是裸数字） | 同（bigint 输出为十进制字面量） | 无 |
| Double | 14（另 3 个在 Data 字段里） | JSON 数字；Jackson 写法，如 `1.4285714285714284E14` | JS 写法 `142857142857142.84` | 树相等（数值相同），字节不同，见下 |
| Decimal | 11 | 字符串 `"15.41"` | 同 | 无 |
| Text | 104 | 字符串 | 同 | 无 |
| Bool | 176 | `true` / `false` | 同 | 无 |
| List | 3 + 探针 | 数组 | 同 | 无 |
| Map | 探针 | 对象，插入序 `{"z":1,"b":2}` | 同 | 无 |
| Data | 77 | `{"__type":"<类型名>", <字段…按声明序>}` | 同 | 无 |
| Enum | 7 | `{"_enum":"Tier","value":"Gold","variant":"Gold","args":[]}` | **多一个** `"__type":"?"` | 删除 `__type == "?"` 的键 |
| Maybe | 37 | `{"__type":"Some","value":v}` / `{"__type":"None"}` | 同 | 无 |
| Result | 31 | `{"__type":"Ok","value":v}` / `{"__type":"Err","value":v}` | 同 | 无 |
| Verdict | 98 | `{"__type":"Verdict","outcome":…[,"role"][,"reason"]}` | 同 | 无 |
| DateTime / PII | 0 | 语料与探针均未产出 | — | T1 补夹具时先在本地平台取树形再写入 VALUE-FORMS |

- **`canonicalJson` 不可用于值（推翻原 Global Constraints「值的字节形态」）**：ts `canonicalJson` 与 core `CanonicalJson.canonicalJson` 在空 TypeContext 下都对非整数数字报 `NON_INTEGER_NUMBER`、对超出 ±(2⁵³−1) 的整数同样报错。960 个 case 里 17 个（全部 Double 结果，含 Data 内的 Double 字段）会因此失败，Long 探针同理。两套 canonical JSON 是为回放哈希设计的（金额必须走 Decimal），不能直接拿来序列化任意结果值。
- **值规范 JSON**（新增；DateTime 与 PII 值的树形本次未取得，在 T1 用本地平台补齐前不在包格式承诺内，VALUE-FORMS 明列为「未定」，导出检查（P2）对返回类型含二者的入口拒绝导出直至补齐；`conformance/package-v1/VALUE-FORMS.md` 规范化，T3 `value-json.ts` 与 T8 `ValueJson.java` 各实现一份并跑同一组向量）：对象键按码点升序；无空白；字符串按 RFC 8785 §3.2.2.2 转义；整数（含 Long，不限 2⁵³）输出精确十进制；非整数 Double 按 RFC 8785 §3.2.2.3（ECMAScript `Number::toString`，最短往返表示）输出，`-0` 输出 `0`；NaN / ±Infinity 不可能出现在值里（出现即 `EVAL_ERROR`）。JVM 侧由 `Double.toString`（JDK 19 起为最短往返位数）取有效数字后按 ECMAScript 规则重排指数形式；向量至少覆盖 `3.5`、`0.3333333333333333`、`1.4285714285714284E14`、`1e21`、`1e-7`、`5e-324`、`-0.0`、`2⁵³+1`（Long），另加以固定种子生成的 10 000 个随机 double（位模式均匀取样，排除 NaN / ±Infinity，以 Node `String(x)` 为期望），两侧逐条比对。Long 超出 2⁵³ 时输出精确十进制数字，消费方需要精度时必须用大数 JSON 解析器读取，README 写明。
- **与平台的关系**：`/evaluate-json` 的 `result` 是 Jackson 输出（插入序、Double 用 Java 写法），值规范 JSON 是同一棵树的另一种确定性写法，两者**树相等、字节不等**。因此 ADR §4.1「`<V>` 的序列化与 aster-api `/evaluate-json` 结果里的值逐字节相同」与 §5.3 P2 黄金门须改为「把平台 `result` 经同一值规范 JSON 序列化后与 CLI 的 `<V>` 逐字节相同」（修订 A1）。
- **入口选择（新发现，影响 T7 与 P2 导出检查）**：`/evaluate-json` 走的是 `DynamicCnlExecutor.executeCoreIrJson`，不是 `TrufflePolicyRuntime`：`CoreIrJson.read` → `EntryPointSelector`（显式名 > `@entry` > 单 Rule > 否则 `ambiguous`）→ `NamedContextMapper` → Jackson 重序列化 IR → `CoreIrEntrySelector.withEntry`（把目标 Func 的原文切片挪到所有 Func 之前；Truffle 的 Loader 只认 `AsterConfig.DEFAULT_FUNCTION`（环境变量 `ASTER_TRUFFLE_FUNC`，缺省 `main`）→ `main` → 第一个 Func）。`TrufflePolicyRuntime.executeFunction` 本身**不按名字取成员**，入口在编译期由 `PolicyEvaluationService.toCompiledPolicy` 经同一个 `CoreIrEntrySelector` 排好。由此三条：①T7 必须把 `CoreIrEntrySelector` 与 `EntryFunctionException` 一起复制进 `aster.truffle.embed`，原 T7 Step 3「按函数名取成员」作废；②模块里存在 `main`（或 `ASTER_TRUFFLE_FUNC` 指定的名字）而入口是别的函数时，JVM 无法执行该入口（`withEntry` 抛 `shadowed`），ts 却能执行——语料 `entry_annotation.aster` 选 `helper` 就是这一类（spike 里 ts 得 42、平台执行了 `main` 得 22，是工具给 `helper` 补 `@entry` 后两个 `@entry` 并存造成的，不计为引擎差异）；P2 导出检查须拒绝这种入口（或 manifest 只列 JVM 可执行的入口），T1 的 `a-multi-entry` 夹具不得含 `main`；③JVM CLI 必须忽略 `ASTER_TRUFFLE_FUNC`（启动时若已设置，`AsterConfig` 在类加载时读取，CLI 以 `ENTRY_NOT_FOUND` 以外的方式无法纠正，故在 `main` 里检测到该变量即 `USAGE` 退出），并有测试。
- **输入约定**：0–5 个形参的 959 个 case（0 参 126、1 参 483、2 参 289、3 参 55、4 参 3、5 参 3），按形参名的对象与位置数组得到的平台结果全部相同（唯一例外即上条的 `entry_annotation` 工具产物）。平台的 `NamedContextMapper` 比 CLI 宽松：任一键命中形参名即按命名格式；一个都不命中且单参时把整个对象当那一个实参；未知键只警告；还会把德语变音（ü→ue 等）模糊匹配。CLI 取它的严格子集，结果与平台相同：
  1. `--input` 必须是对象，键恰为全部形参名（逐字节，不做变音模糊匹配）；缺键、多余键 → `INPUT_INVALID`；0 参入口只接受 `{}`。
  2. JSON 整数超出 ±(2⁵³−1) → `INPUT_INVALID`（探针：输入 `9007199254740993`，ts 解析成 …992 后得 …992，平台 Jackson 保留精度得 …994；两侧都按 JSON 数字读就会分叉）。Long 形参的大值以十进制字符串给出，由 `schema/input.json` 声明。
  3. Decimal 只接受字符串（原计划已有）。

- **col 差异的形态**：对照组每个样本中位数 1 个 origin 节点不同（最多 63），别名组中位数 14.5（最多 472），词汇组 18。抽 80 个 en-US 样本逐节点归类（2 692 个 origin 节点中 241 个不同）：`Name.end` 138、`Module.end` 80（每个样本都有：ts 报文件末行 col 1，Java 报 col 6）、`Name.start` 9、`Call.start/end` 14。别名样本的差异更多，是因为 Java 的 col 指规范化（别名替换回规范拼写）后的文本，ts 指原文。aster-lang-test `ir --full` 门（ADR 0055 §6）本就把「删除全部 `origin.start.col` / `origin.end.col`」作为全局比较投影，col 不参与语义；求值也不读 col。
- **别名叠加语义**：Java `AliasOverlayLexicon.wrap` 是「base 别名在前、用户别名按 kind 追加去重」；原 T3 写的 `resolve-policy-types.ts:52-57` 是 `{ ...base.aliases, ...aliasSet }`，**同 kind 时替换**而非合并。四个内置词法表两侧当前都没有 base 别名（ts `lexicon.aliases` 为 `undefined`，Java `getAliases()` 为 `{}`），所以今天两种写法结果相同；T3 仍须按合并语义实现，避免将来某词法表加了 base 别名后静默分叉。
- **别名校验**：ts `compile` 不校验 aliasSet——单词别名（`liefere`、`给出`）与非规范大小写（`In the case that`）ts 照常编译，平台 `UserAliasValidator` 一律拒绝（「必须是多词短语」「含非规范空白/大小写」）。B 包的 aliasSet 来自平台已校验并签名的 manifest，`run` 不受影响；但 `aster compile <file.aster> --alias-set` 在 Node 上会接受平台拒绝的别名，两侧 `compile` 子命令结果不同。T3 须把 `UserAliasValidator` 的规则（多词、规范形、kind 白名单、`allowStructural` 门、不遮蔽、不撞词汇）移植到 ts，Node 与 JVM 的 `compile --alias-set` 对同一份非法 aliasSet 都报 `COMPILE_ERROR`；校验向量取 aster-api `UserAliasValidatorTest` 与 `UserAliasCompileTest` 的用例。
- **ts issue**：原 T0.4 Step 3 要求「有差异则为每类开 ts issue」。唯一的差异类别是 origin col（ts 与 core 两侧的位置约定不一致，不只是 ts 的问题），在修订 A2 之下不阻塞 P1；建议另开一个跨仓 issue 追踪「ts / core origin col 对齐」，对齐后 A2 的投影仍然成立，不需回改包格式。本次未开 issue，交由用户决定。

### 5. 对 ADR 0059 的修订建议

ADR 在 PR #552 分支上；以下修订随该 PR 或冻结结束后的 docs PR 落地，本计划先按修订后的口径执行。

> **门**：A0–A5 须先合入 ADR 0059（PR #552 分支，或冻结结束后的 docs PR），T1 才能开始；ADR 保持 ACCEPTED，修订作为 §12 裁决记录追加。

- **A0（§4.1：跨 CLI 一致性的比较口径）**：信封 `meta.engine` / `meta.cliVersion` 两侧按定义不同，ADR 与本计划的「两 CLI stdout 逐字节相同」均指把这两个值替换为占位符后逐字节相同（Review Focus 1）；`version` 子命令不参与跨 CLI 比较。这是原计划自身的矛盾，审查时发现，一并修正。
- **A1（§4.1、§5.3：值的字节形态）**：§4.1 「`<V>` 的序列化与 aster-api `/evaluate-json` 结果里的值逐字节相同（§5.3 的共享编解码）」改为「`<V>` 是求值结果的 JSON 树按包格式的『值规范 JSON』序列化（`conformance/package-v1/VALUE-FORMS.md`：键码点升序、整数精确十进制、非整数 Double 按 RFC 8785 数字规则）；该树与 aster-api `/evaluate-json` 的 `result` 树相等」。§5.3 「同一批探针在 aster-api 与 jre CLI 上输出逐字节相同」改为「把 aster-api 的 `result` 经同一值规范 JSON 序列化后，与 jre CLI 的 `<V>` 逐字节相同」。理由：T0.3 实测 Jackson 的 Double 写法（`1.4285714285714284E14`）与插入序键序不可能与任何跨语言规范形式逐字节相同，而两套现有 canonical JSON 都拒绝 Double。
- **A2（§3 manifest、§4.2：IR 漂移判据）**：manifest `coreIr` 增加 `positionFreeSha256` = 「规范 Core IR v2 字节解析后删除每个 `origin` 对象下 `start.col` 与 `end.col`，再按 ADR 0055 §5 的规范 IR 序列化（键码点升序、无空白）后的 SHA-256」（与 aster-lang-test `ir-byte-parity.mjs` 的比较投影同一定义）。规范算法是结构化的：先按 Core IR v2 schema 严格读入（ts `readCoreIr` / core `CoreIrJson.read`，不通过即 `PKG_IR_DRIFT`），再只删除每个 `origin` 对象的 `start.col` 与 `end.col`，然后按规范 JSON（键码点升序、无空白；Core IR v2 中只有字符串与安全整数，Double / Long 字面量都以字符串承载）序列化后求 SHA-256；不得用全局文本替换实现。T0.4 spike 里用正则删除全部 `"col":<整数>,` 只用于判定差异类别，不是规范实现。`coreIr.sha256` 保留为平台 IR 的精确字节身份（审计、A 包 `compiled/core.json` 交叉校验、`meta.coreIrSha256`）。§4.2 改为：「B 在本地编译后，**两个 CLI 都**按 `positionFreeSha256` 比对，不等 → `PKG_IR_DRIFT`；判据是去掉位置列后的 IR 字节」，理由段补一句「origin col 是诊断位置，不参与求值，ADR 0055 §6 的 `ir --full` 门已把它作为全局投影；T0.4 实测 ts 与 Java 在 682 / 682 个编译请求上除 col 外逐字节相同」。两侧统一用投影哈希（而不是 JVM 用精确哈希、Node 用投影哈希），保证同一 B 包在两个 CLI 上的信封逐字节相同。
- **A3（§9：体积上限）**：node-a 8 MiB → **1 MiB**（实测 0.60 MiB × 1.5），jre-a 48 MiB → **18 MiB**（实测 11.84 MiB × 1.5，前提是排除 quarkus 与 ANTLR 工具链）。实测对象是 spike 产物而不是最终 CLI，故加一句：「T5 / T9 首次产出正式 `aster.mjs` / `aster-cli.jar` 时，若超出 P0 值，可按同一规则以正式产物重定一次基线并写回本节；此后改动须修订 ADR」。
- **A4（§4.3：资源）**：补「Node 求值 Worker 以 `resourceLimits.stackSizeMb = 32` 启动（缺省 4 MiB 栈在 3 000–4 000 层就溢出，`maxCallDepth = 10 000` 无从生效）；JVM CLI 在缺省线程栈上求值（与 aster-api 一致，不调 `-Xss`），实测 1 000–2 000 层即 `RESOURCE_EXHAUSTED`。两侧在约 2 000–10 000 层之间结果不同，属本节排除在承诺之外的资源类结果」。
- **A5（§5.1：导出时拒绝）**：增加两条导出检查。**E736**：入口函数名不是 `main`、而模块里存在名为 `main` 的函数 → 拒绝该入口（JVM 的入口选择会被 `main` 抢占，`CoreIrEntrySelector` 报 `shadowed`；Node 能执行，两侧必然不一致）。优先入口集合固定为 `{main}`：JVM CLI 拒绝 `ASTER_TRUFFLE_FUNC`（T8），导出检查也只按 `main` 判定；诊断写明被抢占的入口名与 `main`。若平台进程设置了 `ASTER_TRUFFLE_FUNC`，导出端点回 503，错误码 `export_runtime_misconfigured`，不按该值放宽或收紧。**E737**：入口的形参类型或返回类型中（递归遍历一切类型构造：`List`、`Map` 的键与值、`Maybe` / `Option`、`Result` 的两侧、Data 的全部字段、Enum 变体参数、函数类型的参数与返回、类型别名展开；展开别名与 Data 时维护已访问集合，防递归类型死循环）出现 DateTime 或 PII 类型 → 拒绝，诊断给出类型路径（如 `return.List<Claim>.filedAt: DateTime`），直到 VALUE-FORMS 补齐二者的规范树形并修订本条；T1 夹具无此类入口，P2 补嵌套类型拒绝用例（至少 `List<Data{DateTime}>` 与 `Option<PII>` 各一）。
